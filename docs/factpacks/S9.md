# S9. Speed at 10k to 100k

Date: 2026-10-24. Pong alignment and the default bar image are faster. Other outputs stay the same bytes. `--align-method` still defaults to greedy. No new dependency.

## What changed

`pong_sim` still keeps rows with `a + b > 0`. If none remain it returns 0. Otherwise it subtracts the kept entries in index order and calls `np.dot` on that vector, then `1 - sqrt(dot / (2n))`. When every entry is kept, that subtraction is the two contiguous vectors. A shorter mask still uses the boolean index.

`match_next_pong` scores each raw column pair once and each merged column `new[:, a] + new[:, b]` once. The assignment matrix is filled from those values. The split comparison uses the cached raw similarities. On K = 2 to 12 the similarity body runs 3000 times. The previous pair loop ran it 22184 times on the same chain.

`ancestry_image` stores the pixel key `(height - 1 - y) / height + 1e-12`. On a finite non-decreasing cumulative row, the column index is how many bounds are `<=` that key, in blocks of 4096 samples. Any other row uses `searchsorted` on `cumsum` of that row and the same keys. Pixels past the last bound stay white. The matrix dtype is left as it was.

`col_pearson` is unchanged. A constant column still returns 0 before centering.

## Why the outputs match

The pong float is the same mask, the same subtraction order, and the same `np.dot`. Caching stores those floats and reads them back. It does not use a sum of squares along another axis.

On a sorted finite row, `searchsorted(..., side="right")` is the number of entries `<=` the key. That number is an integer count, so the order of the additions does not change the index. A row that is not finite or not non-decreasing takes the previous `searchsorted` path. Column 0 of Q stays at the bottom of the bar.

## Pair table memory

The merged columns of one step are `N * k * (k - 1) / 2 * 8` bytes, and a second contiguous copy of that block was allocated while the columns were scored. On Apple M1 Pro (`machdep.cpu.brand_string`), `hw.model` = `MacBookPro18,3`, `hw.memsize` = 17179869184, Python 3.9.6, numpy 2.0.2, scipy 1.13.1, Pillow 11.3.0, one pong run at N = 100000 and K = 2 to 20 took 409.48 s and 304922624 bytes before this speedup, and 4.88 s and 1327955968 bytes when each step kept its own table.

A fresh `/usr/bin/time -l` run of that per-step table, same machine, seed `20261022`, Dirichlet draws, was real 6.09 s and maximum resident set size 1365770240 bytes (align 5.642 s). K = 2 to 12 on that same run shape was real 1.04 s and 475971584 bytes (align 0.866 s), in line with the three-run median above.

The block is allocated once inside `align_qs`, for the largest K, and passed into `match_next_pong`. A direct call allocates its own block. The merged column is `new[:, a] + new[:, b]` in the input dtype, and `pong_sim` upcasts that sum. Those upcast values are written into the Fortran-order block, so a column is already contiguous and is not copied again. The block is dropped when that alignment returns. One `/usr/bin/time -l` run of this form: K = 2 to 20, real 4.39 s, maximum resident set size 671072256 bytes (align 3.914 s). K = 2 to 12, real 0.84 s, 331153408 bytes (align 0.668 s). The resident set is lower than a fresh table at every step, so the reuse stays. N = 10000, K = 2 to 12 pong output directories still match the previous tree (`differ=0`). The suite reported `Ran 311 tests in 14.433s`, `OK (skipped=20)`.

## Left as written

`col_pearson`, greedy `match_next`, `pearson_matrix`, and `jaccard_matrix` were not hot, and they were not rewritten. Jaccard's integer counts matched on 20 matrices. The function was 0.007 s at N = 10000, so that form was not used.

clumpp-full at N = 10000 spent 9.420 s and then stopped because K+1 was 9. clumpp-greedy spent 8.419 s and stopped the same way. The time is `matrix_gprime` (46230 calls, 4.832 s) and `_best_gprime_perm` (6 calls, 3.270 s). Reusing buffers on the K = 8 step was 6.509 s and 6.442 s, with the same permutation `[2, 6, 0, 1, 3, 5, 4, 7]`. That draft was not kept. clumpp-largek was 0.022 s. clumppling-ilp was 0.055 s. Those four methods were not rewritten.

At N = 10000 before this change, pong `align_qs` was 1.266 s, of which `pong_sim` was 1.136 s (22184 calls). After this change, a second pong `align_qs` in a process that had already imported scipy was 0.070 s, of which `_pong_one` was 0.040 s (3000 calls). The default command fell from 21.729 s to 1.844 s in one profiled run. `ancestry_image` fell from 8.334 s (cum 20.581 s, including 13200000 `searchsorted` calls at 5.202 s) to 0.625 s (cum 0.762 s).
